# Track Execution Order

Accepted order:

1. A0 - convergence / preflight
2. Track A - representation and view-model spine
3. Manual Observation Batch 0
4. Track B - Eureka Node, work units, candidates, source/evidence/review loop
5. Track D - snapshot and relay substrate
6. Track C - native clients
7. Track E - hosting and operations

## A0 - Convergence / Preflight

`EUREKA-CONVERGE-01` reconciles stale prompt order, P-number fragments, public
alpha wording, AIDE queue state, and future track gates. It creates no product
behavior.

## Track A - Representation And View-model Spine

Track A goes first because future pages, search results, static projections,
snapshots, native clients, relay consumers, and hosted public surfaces all need
the same representation, host-profile, compatibility, evidence, and action
vocabulary before implementation broadens.

Track A should use existing object/source/comparison/identity/ranking contracts
as inputs, but it must avoid runtime rewrites and public truth overclaims.

## Manual Observation Batch 0

Manual Observation Batch 0 remains human-operated. It should run after Track A
clarifies the view-model and observation targets, but before Track B treats
external baseline comparison as evidence.

## Track B - Node, Work Units, Candidates, Source/Evidence/Review Loop

Track B absorbs old query intelligence, miss ledger, search need, probe queue,
candidate, source cache, evidence ledger, connector approval, staging, and pack
import planning. It must preserve the rules that candidates are not truth,
approval packs are not connectors, dry-runs are not runtime mutation, and source
observations need evidence/provenance review.

## Track D - Snapshot And Relay Substrate

Track D comes before Track C because native clients need stable offline/static
inputs before project creation. Snapshot contracts, signed/unsigned posture,
file-tree/text/lite consumers, relay security, and local relay substrate must be
clear before a native shell depends on them.

Track D must still avoid production signed snapshots, executable downloads,
relay sockets, private-data serving, live backend proxying, and live probes
until separate reviewed tasks authorize them.

## Track C - Native Clients

Track C starts only after Track D clarifies snapshot and relay substrate. Native
clients must consume governed contracts and public/static/snapshot/relay inputs,
not engine internals. No Visual Studio/Xcode project or native GUI should be
created before an explicit Track C task approves the first lane.

## Track E - Hosting And Operations

Track E remains last because hosting amplifies claims. Actual hosted public
alpha requires operator evidence for static hosting, backend URL, DNS/TLS,
abuse controls, rate limits, monitoring, rollback, disabled live probes, source
policy, and public claim traceability.

Early public-alpha-shaped work in the repo means local, static, staged, or
localhost rehearsal evidence. Actual hosted public alpha means Track E only.
