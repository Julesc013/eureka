# Contradictions and Drift

## 1. Search engine versus artefact resolver

Older framing treats Eureka as a better search engine or public search product. Later synthesis repeatedly reframes it as an evidence-first temporal object/artefact resolver. This is not a hard contradiction if “search” remains the public entry point and “resolution” becomes the architecture.

## 2. Public alpha versus product reality

Some prompt sequences discuss public alpha hardening. Later chats reject launch from an empty shell and make reviewed-corpus growth plus local Workbench proof the real machine. The drift should be resolved in favor of honest local proof before public claims.

## 3. Reported IA pilot versus full Archive.org integration

Multiple packages say IA metadata pilot work was completed through local proofs. The same packages insist this does not mean full Archive.org integration. The distinction must be preserved: metadata-only source-family proof is not crawling, downloads, files, Wayback replay, or hidden-member extraction.

## 4. P-number queue versus track queue

The archive contains P50–P107/P108-style planning and later Track A/B/D/C/E/F–L planning. This creates sequence ambiguity. A Track 0/current-state convergence task is the clean way to map old queue items to new tracks.

## 5. Branch/generated-state conflict

One planning archive reports a concrete lesson: generated repo-health can claim branch equality while live branch comparison shows divergence. This is a canonical drift warning. Generated state is advisory; live repo authority wins.

## 6. Manual observations: human-operated versus agent-assisted

One package treats Manual Observation Batch 0 as human-operated because external observations must not be fabricated. A later package says manual observations should become agent-assisted. These can be reconciled by letting agents prepare candidate observations and requiring human/operator review before they become evidence.

## 7. Workbench-first versus Track A/TSIS-first

Workbench packages emphasize local product proof. Track convergence and TSIS notes emphasize representation contracts before later surfaces. The compatible ordering is: verify state; add semantic/representation contracts; then use them to build Workbench-visible run lanes.

## 8. Directory expansion versus stable roots

One loose TSIS note explores a larger root structure with renderers/skins/services/apps/data/infra. The later loose note rejects that expansion and says to keep Eureka’s current roots, adding TSIS inside contracts/runtime/surfaces/site/snapshots/tests/control. The later note should be treated as the cleaner advisory direction.

## 9. Same code everywhere versus same contracts everywhere

The corpus sometimes gestures at one system across old browsers, rich web, native, terminal, snapshots, and agents. The later TSIS correction is more precise: same contracts, routes, view models, action model, policy decisions, and evidence; different renderers and adapters.

## 10. AI deferred versus future AI/agent support

Near-term AI/model runtime is repeatedly deferred and prohibited from truth-making. Later representation planning includes agent-context outputs. This is not a conflict if AI/agent surfaces remain consumers or candidate generators under policy and review, not authorities.
