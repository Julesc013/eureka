# Source Blocks for Future Book — Eureka Workbench, IA Connector, and Production Path

## Block 1 — The Workbench as Internal Superset

Type:
- decision / rationale

Source status:
- FACT for visible wording; decision status is best treated as strong proposed doctrine unless later user confirmation exists.

Text:
The Workbench should be the internal superset of the final Eureka product. Not a throwaway admin page. Not just a developer dashboard. Not a temporary UI. It should be one overpowered local/operator workbench that uses the same backend contracts, search/result/view models, review/index/source machinery, components, and routes where possible. The public app should later be a constrained, safe projection.

Why this block matters:
This is the clearest architectural synthesis in the chat. It can anchor a future chapter on Eureka’s product surface strategy.

Suggested future chapter/theme:
Workbench as Mission Control; One Kernel, Many Projections.

## Block 2 — Progressive IA Search Instead of Blocking Deep Crawl

Type:
- rationale / rejection

Source status:
- FACT as a visible assistant recommendation; user acceptance not explicitly shown after the final response.

Text:
Build a complete Internet Archive end-to-end local search connector, but do not define it as a single request that searches and deeply indexes all archive.org while the user waits. The right model is a progressive local discovery engine: reviewed index first, candidate/source-cache lanes next, IA metadata jobs, review, and later index rebuilds.

Why this block matters:
This captures the main product correction around the user’s desire for full IA search.

Suggested future chapter/theme:
Source Connectors and Progressive Discovery.

## Block 4 — Scaffolding Is Not Product

Type:
- rationale / risk

Source status:
- FACT as a visible theme; specific repository assessment depends on then-current branch state.

Text:
The project had generated many policy packs, audit packs, fixture contracts, candidate schemas, validator scripts, boundary reports, and non-claim docs. Some of that was valuable, but a real product needs domain models, runtime services, storage, query paths, source observation, evidence ledger, review workflow, index rebuild, public API, public UI, and tests proving behavior.

Why this block matters:
This is a core anti-failure-mode lesson for agent-driven software projects.

Suggested future chapter/theme:
Avoiding Prompt-Shaped Architecture.

## Block 8 — Public Product as Projection

Type:
- architecture / rationale

Source status:
- FACT as visible assistant recommendation; user acceptance not explicit after final response.
