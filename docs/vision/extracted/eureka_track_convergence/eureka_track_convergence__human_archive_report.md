## 7. Rationale, Tradeoffs, and Design Logic

The visible reasoning in this chat was driven by trust boundaries. Eureka’s domain creates unusual safety and correctness risks: historical software and archive materials are often mislabelled, mirrored, nested, obsolete, rights-sensitive, malware-prone, and compatibility-dependent. The project therefore cannot optimize only for recall or speed. It must optimize for evidence, provenance, review, and explanation.

The biggest tradeoff was between moving quickly toward a live product and preserving the system’s evidence-first architecture. Earlier plans emphasized hosted local-index search sooner. The new track plan moved hosting later, after representation, contribution/evidence, relay, and native-consumption layers. This slows public launch but reduces the risk of launching surfaces whose semantics drift from each other or whose claims exceed their evidence.

Another tradeoff was between more contracts and more runtime. The project already has many contracts and dry-runs. The assistant repeatedly warned that more horizontal architecture expansion could become document-heavy. At the same time, the new track plan still begins with contracts because representation must be coherent before runtime surfaces are refactored. The optimal middle path identified in the chat is not “no more contracts” but “contracts that immediately constrain runtime and prevent drift.”

A further tradeoff concerned manual external baselines. Manual Observation Batch 0 is a truth blocker, but the user moved it after Track A. That delays comparison evidence but improves downstream usefulness: observations can be converted into SearchNeed, WorkUnit, NeedPage, CandidatePage, and Absence fixtures rather than remaining loose notes. The risk is that external truth remains zero for longer. The mitigation is to keep Batch 0 high priority and methodologically strict.

The assistant’s proposed Track 0 was based on a second-order risk: roadmap drift. The project has old P-number tasks, new track tasks, AIDE queue metadata, audit packs, inventory files, and status reports. If the transition is not formalized, future assistants might treat historical next-step recommendations as current, duplicate tasks under new names, or lose important old work. Track 0 is designed to make the execution model durable.

The representation-first logic also has second-order consequences. If all surfaces derive from canonical view models, then old-browser HTML, text files, JSON/API, snapshot manifests, relay responses, and native cards can preserve the same semantics. If this is misunderstood and each surface is built independently, the project could develop inconsistent definitions of identity, evidence, risk, rights, compatibility, actions, gaps, and absence.

The connector logic is similarly cautious. A connector result is not truth; it is a source-cache observation or evidence candidate that must go through review. This avoids treating live metadata as accepted public truth and avoids public-query fanout. The first connector pattern should be one complete metadata-only path, not many partial connectors.

The native-client plan reflects a compatibility tradeoff. Building native apps early could be attractive, but if they depend on unstable backend APIs they will become brittle. Building snapshot and relay first gives old systems and native clients stable, read-only inputs. This is slower but more durable.

The risks if this context is misunderstood are substantial. A future assistant might treat `P107 complete` as permission to integrate public ranking. It might treat the new Track A/B/D/C/E plan as accepted including all assistant additions, when only the user’s proposed plan was explicitly stated. It might treat pasted repo reports as independently verified facts. It might treat external baseline readiness as external baseline completion. It might treat “authoritative local store” as “truth.” The archive should prevent those errors.
